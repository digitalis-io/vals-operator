# Usage

Two custom resources drive the operator:

- **`ValsSecret`** (`digitalis.io/v1`) — sync values from any vals backend into a
  Kubernetes Secret, and optionally rotate database passwords.
- **`DbSecret`** (`digitalis.io/v1beta1`) — issue dynamic database credentials from
  the Vault/OpenBao database secrets engine and keep the lease renewed.

## ValsSecret

```yaml
apiVersion: digitalis.io/v1
kind: ValsSecret
metadata:
  name: vals-secret-sample
  labels:
    owner: digitalis.io
spec:
  name: my-secret # Optional, defaults to the resource name
  ttl: 3600       # Optional, default 5 minutes. How often the backend is re-read.
  type: Opaque    # Optional, default Opaque. Any Kubernetes Secret type.
  data:
    username:
      ref: ref+vault://secret/database/username
      encoding: text
    password:
      ref: ref+vault://secret/database/password
      encoding: text
    ssh:
      ref: ref+vault://secret/database/ssh-private-key
      encoding: base64
    aws-user:
      ref: ref+awssecrets://kube/test#username
    aws-pass:
      ref: ref+awssecrets://kube/test#password
    ns-secret:
      ref: ref+k8s://namespace/secret#key
    plain-text:
      ref: literal_name # No ref+ prefix: stored verbatim, not looked up
  template:
    config.yaml: |
      # Config generated by Vals-Operator on {{ now | date "2006-01-02" }}
      username: {{ .username }}
      password: {{ .password }}
  rollout: # Optional: restart workloads when the secret changes
    - kind: Deployment
      name: myapp
```

This creates a Secret named `my-secret` and keeps it in sync with the backend.

### Fields

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | resource name | Name of the Kubernetes Secret to create. |
| `data` | map | required | Keys of the Secret, each with a `ref` and optional `encoding`. |
| `ttl` | integer (seconds) | operator `-ttl`, `5m` | How often this secret is re-read from the backend. |
| `type` | string | `Opaque` | Kubernetes Secret type. |
| `template` | map | — | Extra Secret keys rendered from Go templates. |
| `databases` | list | — | Databases whose password is rotated to match. See [Password rotation](#password-rotation). |
| `rollout` | list | — | Workloads to restart when the secret changes. `kind` is `Deployment` or `StatefulSet`. |

`ttl` exists to limit how often the operator calls the backend — some stores, such as
[AWS Secrets Manager](https://aws.amazon.com/secrets-manager/pricing/), charge per
call.

`encoding` defaults to `text`. Set it to `base64` to have the operator base64-decode
the value it fetched before storing it, which is how you carry binary blobs and large
configuration files through a backend that only holds strings. It has no effect on
`ref+k8s://` references, whose values are already raw Secret data.

Set the annotation `vals-operator.digitalis.io/record: "true"` on the resource to
record an Event on every update when the operator runs with `-record-changes=false`.

### Templates

Any key in `data` is available as a template variable, so you can assemble a whole
configuration file out of individual secret values. Templates use Go's
[`text/template`](https://pkg.go.dev/text/template) with the
[sprig](https://masterminds.github.io/sprig/) function set, **except** `env`,
`expandenv` and `getHostByName`.

Those three are removed deliberately. Templates come from namespaced resources but are
rendered inside the operator, so they would expose the operator's own environment —
including its Vault/OpenBao token — to anybody able to create a `ValsSecret` or
`DbSecret`. A template using one fails with `function "env" not defined`. Put the
value in your secrets backend and reference it from `data` instead.

### Mirroring secrets between namespaces

`ref+k8s://namespace/secret#key` reads a key from a Kubernetes Secret in another
namespace and keeps it in sync.

> **Warning:** this is subject only to the *operator's* RBAC, not the requesting
> namespace's. In a multi-tenant cluster, restrict it — see
> [Security](security.md#cross-namespace-references).

## DbSecret

> Requires Vault >= 1.10 or OpenBao >= 2.0.

Vault and OpenBao can generate
[database credentials](https://developer.hashicorp.com/vault/docs/secrets/databases)
on demand. `DbSecret` puts those credentials into a Kubernetes Secret and renews the
lease before it expires.

```yaml
apiVersion: digitalis.io/v1beta1
kind: DbSecret
metadata:
  name: cassandra
spec:
  secretName: cassandra-credentials # Optional, defaults to the resource name
  renew: true                       # Renew the lease instead of issuing new credentials
  vault:
    mount: cass000                  # Database secrets engine mount
    role: readonly                  # Role to request credentials for
  template:                         # Optional: rename or reshape the keys
    CASSANDRA_USERNAME: "{{ .username }}"
    CASSANDRA_PASSWORD: "{{ .password }}"
  rollout:
    - kind: Deployment
      name: cassandra-client
    - kind: StatefulSet
      name: cassandra-client-other
```

Without a `template`, the Secret holds `username` and `password` as returned by the
backend.

The mount must be a database secrets engine configured for your database. Vault and
OpenBao ship plugins for PostgreSQL, MySQL, Cassandra, Elasticsearch and others out of
the box. **ClickHouse is not one of them** — to issue dynamic ClickHouse credentials
you need a database plugin such as
[openbao-plugin-database-clickhouse](https://github.com/digitalis-io/openbao-plugin-database-clickhouse),
registered in OpenBao before the mount is created.

> Note this is separate from the `clickhouse` rotation driver under
> [Password rotation](#password-rotation), which changes an existing user's password
> and needs no backend plugin.

### Fields

| Field | Type | Default | Description |
|---|---|---|---|
| `vault.mount` | string | required | Database secrets engine mount. Single path segment. |
| `vault.role` | string | required | Role to request credentials for. Single path segment. |
| `secretName` | string | resource name | Name of the Kubernetes Secret to create. |
| `renew` | bool | `false` | Renew the existing lease rather than issuing new credentials each cycle. |
| `template` | map | — | Rewrites the Secret keys. Variables: `.username`, `.password`. |
| `rollout` | list | — | Workloads to restart when the credentials change. `kind` is `Deployment` or `StatefulSet`. |

`vault:` is the field name for both backends; it configures whichever of Vault or
OpenBao the operator is connected to.

The operator will not write to a Secret it does not own, so `secretName` cannot be
pointed at an existing unrelated Secret.

## Rollouts

`rollout` restarts workloads so they pick up the new value. The operator stamps the
pod template with a `vals-operator.digitalis.io/restartedAt` annotation, which makes
the controller roll the pods — the same mechanism `kubectl rollout restart` uses with
its own annotation.

The target must live in the same namespace as the `ValsSecret` or `DbSecret`. A target
that does not exist is logged and skipped, not treated as an error.

Only `Deployment` and `StatefulSet` are supported. `kind: Pod` is rejected by the
`DbSecret` API and fails at reconciliation for a `ValsSecret`.

## Password rotation

A `ValsSecret` can also push the value it fetched into the database itself, so the
secrets store, the Kubernetes Secret and the database stay in step. This is how you
rotate a database password without touching the applications — provided your clients
re-read the Secret and reconnect when it changes.

Supported drivers: `cassandra`, `postgres`, `mysql`, `clickhouse`, `elastic`.

> TLS between the operator and the database is supported for ClickHouse only.

```yaml
apiVersion: digitalis.io/v1
kind: ValsSecret
metadata:
  name: rotate-db-password
spec:
  name: my-secret
  ttl: 10
  data:
    username:
      ref: ref+gcpsecrets://databases/test#username
      encoding: text
    password:
      ref: ref+gcpsecrets://databases/test#password
      encoding: text
  databases:
    - driver: cassandra
      loginCredentials:
        secretName: cassandra-creds # Secret holding the admin credentials used to run the change
        usernameKey: username
        passwordKey: password
      port: 9042
      usernameKey: username         # Key in this ValsSecret's data holding the new username
      passwordKey: password         # Key in this ValsSecret's data holding the new password
      hosts:                        # All nodes; tried in order until one succeeds
        - cassandra01
        - cassandra02
    - driver: postgres
      loginCredentials:
        secretName: postgres-creds
        usernameKey: username
        passwordKey: password
      port: 5432
      usernameKey: username
      passwordKey: password
      hosts:
        - postgres
    - driver: mysql
      loginCredentials:
        secretName: mysql-creds
        namespace: mysql-server
        usernameKey: username            # Defaults to `root` when omitted
        passwordKey: mysql-root-password
      port: 3306
      usernameKey: username
      passwordKey: password
      userHost: host                     # Optional, see note below
      hosts:
        - mysql
    - driver: elastic
      loginCredentials:
        secretName: elastic-creds
        namespace: elastic-server
        usernameKey: username            # Defaults to `elastic` when omitted
        passwordKey: password
      port: 9200
      usernameKey: username
      passwordKey: password
      hosts:
        - my-elastic                     # Becomes http://my-elastic:9200
        - https://my-other-elastic:9200  # Or give the full URL
```

`userHost` (MySQL only) names a **key in the `loginCredentials` secret** whose value
becomes the host part of the MySQL user — `'user'@'<host>'`. When it is unset, or the
key is absent from the secret, the driver uses `%`.

### ClickHouse

```yaml
apiVersion: digitalis.io/v1
kind: ValsSecret
metadata:
  name: rotate-clickhouse-password
spec:
  name: clickhouse-app-creds
  data:
    username:
      ref: ref+vault://secret/clickhouse/app#username
    password:
      ref: ref+vault://secret/clickhouse/app#password
  databases:
    - driver: clickhouse
      loginCredentials:
        secretName: clickhouse-creds
        usernameKey: username        # Omit to log in as the ClickHouse user `default`
        passwordKey: password
      protocol: native               # native (default, also `tcp`) or http
      tls: preferred                 # preferred (default), disable, require or skip-verify
      port: 9000                     # Default 9000 native, 9440 native+TLS, 8123 http, 8443 https
      usernameKey: username
      passwordKey: password
      hosts:
        - clickhouse01               # Uses the protocol and tls settings above
        - https://clickhouse02:8443  # A scheme on the host overrides them
```

Connection methods:

| Setting | Values | Default port |
|---|---|---|
| `protocol: native` (or `tcp`) | native binary protocol | `9000`, or `9440` with TLS |
| `protocol: http` | HTTP protocol | `8123`, or `8443` with TLS |

TLS is selected with the `tls` field:

| `tls` | Behaviour |
|---|---|
| `preferred` (default) | Connects over TLS and falls back to plaintext if the server does not offer it. The server certificate is not verified, matching the MySQL driver's `tls=preferred`. |
| `disable` | Never uses TLS. |
| `require` | Always uses TLS and verifies the server certificate. |
| `skip-verify` | Always uses TLS without verifying the server certificate. |

Each entry in `hosts` may carry its own scheme, which overrides `protocol` and `tls`
for that host: `tcp://`, `native://`, `clickhouse://` (plaintext native), `tls://`,
`clickhouses://` (native over TLS), `http://` and `https://`. A `host:port` entry
overrides the `port` field. Hosts are tried in order until one succeeds.

**Constraint:** `ALTER USER` only works for users created through SQL-driven access
control. Users defined in `users.xml` cannot be altered at runtime; rotation against
such a user fails with an error from the server and is logged as a failed host.

The ClickHouse backend has integration tests covering every connection method above.
Run them against a throwaway container with `make test-clickhouse` (requires Docker).

## Troubleshooting

The operator records what it did as Kubernetes Events on the resource:

```sh
kubectl describe valssecret my-secret
kubectl describe dbsecret my-db
```

Rejected backend paths, denied cross-namespace references, failed rotations and lease
problems all appear there.
